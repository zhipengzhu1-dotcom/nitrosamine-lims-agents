# Critical data changes need a second person's approval from the first save

A change to critical data (a result value, weight, dilution volume, standard concentration, a Specification's maximum daily dose or acceptable intake, the instrument a Run used, or a Material Lot's certified value, purity, salt form, uncertainty or expiry or retest date) is only a proposal from the moment the value is first saved. It takes effect when a second person approves it, never the person who proposed it. Until then the earlier value stays current, and the Analyst cannot sign Performed while a correction is pending. We chose this because China's computerized-systems annex (Art. 16) requires approval for changes to *entered* critical data. Every entry saves to the server as it is made (FDA DI Q12), so a value is "entered" at its first save. The map designs to the strictest superset of Part 11, draft Annex 11, China and Japan.

## Considered options

- **Free correction until the Analyst signs Performed, approval only after.** Owner's first choice, rejected after the Part 11 expert review: it lets an Analyst overwrite a saved weight or result with only a reason, which is the case Art. 16 targets.
- **Approval from first save, as a separate step.** Rejected as too costly for typo fixes.
- **Approval from first save, folded into existing signings.** Chosen. Before Performed, any pending correction needs a Verified signing by a second person, and that signing approves every pending correction on the record. After Performed, the Reviewer approves corrections to results. A Specification's pending corrections are approved inside QA's Approved signing, which the server refuses from anyone who proposed one of them. In every case the dialog shows each old → new value.

## Consequences

Fixing a typo in a weight is not an edit. It creates a proposed value that a second person sees and approves. "Simplifying" this into an in-place edit with a reason would break the China alignment. Source: [Decide the audit trail and electronic signature design](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/13). The Material Lot fields were added by [Decide the inventory model](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/17), because the server computes standard concentrations from them. An approved correction makes new Record Versions of every descendant Solution, so their Verified signatures show as unsigned until given again.

[Decide the equipment and scheduled-check model](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/15) added Room, storage and DI water readings. Each of those readings alone decides whether an Excursion or Deviation opens, so one person must not be able to correct an out-of-limits reading into limits. The same decision made a Check's typed values Critical Data, such as a balance or pipette weighing, so they are corrected the same way.

[Decide the specification and limits model](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/29) made every field of a Specification, its Sections and its Lines Critical Data, since each can decide a verdict. That includes a fixed or limit-test concentration, a limit's decimal places and units, the reporting threshold, treatment duration, less-than-lifetime factor and attestation, CPCA category, interim end date, rule for multiple nitrosamines, Decision Rule, basis, pharmacopoeial conformance claim and edition, and the limit as the Customer writes it. It also added a Customer-supplied water or LOD value used for a basis correction. The server computes an AI-derived limit, so nobody types it.

The same decision drew the line for Specifications at QA approval. Before QA signs Approved, a change to a Critical Data field is a Critical Data Change approved within that signing. After Approved, any change is a new Specification version: Authored, Approved by QA, and accepted again by the Customer, whose earlier acceptance never carries over. See ADR 0003.

[Decide the Method record's structured data](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/36) generalised that line to every versioned record: Critical Data Change governs a Draft and unversioned records, and after approval any change is a new version. Every structured field of a Method version is Critical Data, held as decimal strings with their unit where it is a number: Analytes, calculation, calibration, replication, variability limit, outlier test, Retest count, reporting precision, Preparation stability, maximum dilution, Run Checks, Equipment performance and Material grades, basis and coverage lists. The same decision added a Method Report's results; a Method Adoption's status, scope entries, LOQ, LOD, range, maximum dilution, cited Method Report version and hash, and validation impact decision; every field of an Uncertainty Evaluation (U, k, range, approach, pinned evidence set, instrument units, matrices) and of an Accreditation Scope (entries, flexible limits, status events, validity dates); manually entered Run Check values; and a Substance's kind, which decides whether a Method may be Verified (basic compendial). Each of these either gates Acceptance or decides a verdict, so one person must not be able to change it alone.

[Decide how results are entered, imported, and reviewed](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/20) set where "first save" falls for imported values. The worker's parsed values are drafts that nobody can edit: the Analyst's confirmation of the whole Import is their first save, and a rejected Import is kept. The same decision added an Injection's match to a Preparation or standard and its exclusion, which needs an assignable cause; a typed Injection's ID or acquisition time; and a Run Adjustment's values. In typed Runs, each typed value (injection IDs and acquisition times included, since they decide Preparation matching and the Fitness Status check) is Verified against the attached True Copy. A Reprocessing is a new Record Version of the Run: before Performed it needs a Verified signing, after Performed a Return, and after release the approved-Deviation path. Tests and dependent Runs carry the ID and hash of every Run Version they used, so a new version shows them unsigned and holds them.

[Decide what is recorded when a failing value is first typed](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/38) replaced #15's "typed a second time to confirm before it saves". A reading or Check value that is implausible or fails its Acceptance Criterion saves at once as an Unconfirmed Value, so its first save is the first entry, not the retype. Only its typist confirms it by retyping. Replacing it with a different value is a Critical Data Change like any other, even though it was never the value of record: the case this ADR exists for is a failing reading turned into a passing one by the person who typed it. While it is Unconfirmed or its replacement is pending it blocks use as if it had failed, without opening a Deviation; a rejected replacement, or the end of the Lab day, makes it the value of record from its first save time. A reading has no signing to fold the approval into, so a person holding a Reviewed Authorisation on its Check Plan approves the replacement by signing the reading Verified. A Check cannot be Abandoned while it holds an Unconfirmed Value or a pending Critical Data Change. The alternative the Part 11 reviewer first proposed, recording the replaced value with no approval, was rejected because it contradicts this ADR.
