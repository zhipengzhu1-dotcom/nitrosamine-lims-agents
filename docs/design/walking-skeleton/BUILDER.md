# Builder contract

Every implementation agent working on this codebase reads this file first and follows it. It started as the contract for the walking skeleton ([Prototype the walking skeleton on main](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/24)) and stays the contract for the modules built on it.

## Where

- Work only in the worktree and branch your prompt names.
- Never touch another session's checkout or uncommitted work.
- Never read or copy anything from `OneDrive_3_9-29-2026/`. All data you write is fictional. Published regulatory values (an Acceptable Intake, a pharmacopoeial limit) are real and cite their source and revision.
- Never push, deploy, force-push or delete data outside your worktree. Use `scripts/pg.sh` for the local Postgres cluster, never its data directory.

## Read first

1. `docs/design/walking-skeleton/RATIONALE.md`: the design, its **Synthesis decision**, and **Implementation reconciliation**, which records how each unit deviated and overrides the design where they differ. Beside it: `module-map.md`, `test-plan.md`, `sessions.md`.
2. `CONTEXT.md`: the domain language. Name things with its terms.
3. The decisions your unit touches: each is a closed ticket on the map ([Map: Nitrosamine LC-MS/MS LIMS prototype](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/1)); read its resolution with `gh issue view <n> --comments`. The ADRs are in `docs/adr/`.

## What exists (build on it, don't rebuild it)

- `packages/domain`: pure rules. Gates, verdicts (ADR 0006, decision 29), machines, refusals, canonical bytes, branded ids.
- `packages/db`: migrations, `runAudited` (the only write path), `seal`, `sign`, `lockReleased`, `versionStands`, the scope seam `openRead`, the test harness `@lims/db/testing`, codegen, and `scripts/mutants.ts`.
- `packages/contract`: the wire DTOs the web app may import.
- `apps/api`: two doors (`GET /api/views/:name`, `POST /api/commands/:name`), the commit pipeline, identity and sessions, the Records module with its kind register, the sample chain, the seed. `apps/api/test/support.ts` shows how to plug in a kind, a command and a view.
- `apps/web`: the Bench Rail components, the session gate, the signing hook, the Recorded Value field.
- `deploy/`: Compose, the Mac scripts and the owner's runbook. Deploys pause for the owner.

## How to build

- Test first, and see each test fail for the reason you predicted before you write the code. Tests run against the real Postgres; database tests connect as `lims_app`, never a superuser except to simulate tampering. Each test file gets its own database cloned from the migrated template.
- Migrations are plain numbered SQL files in `packages/db/migrations/`, applied by the runner as `lims_migrator` under `SET ROLE lims_owner`. The app connects as `lims_app`, which owns nothing.
- Exact decimals only: no JS `number` anywhere a limit, value or verdict flows. Decimal strings keep their written decimals.
- Refusals are values, never thrown. Exceptions mean bugs. Anything outside the build refuses with the domain's `notBuilt` reason and writes one `spec_gap` row.
- Comments only for a non-obvious *why*. No phase-narrating comments.
- Seed and test data stay at or under 8 people, 4 Customers, 13 Products, 3 Methods and 135 Submissions, generated by the seed, never committed as a data file.

## Your gate before you report done

1. `pnpm install --frozen-lockfile`, `pnpm typecheck` and `pnpm test` green from the worktree root. Paste the real summary lines.
2. For each behaviour you own, name the test that proves it and the failure you saw first. Every new database guard (a trigger check, a grant, a constraint that refuses) gets an entry in `packages/db/scripts/mutants.ts`, and `pnpm --filter @lims/db mutants` reports every mutant KILLED.
3. Small single-purpose commits, imperative messages that say what and why, each ending with a blank line and the `Co-Authored-By:` line of the Claude model that wrote it.
4. **Deviations.** Anything you did differently from RATIONALE.md goes in your report and in its "Implementation reconciliation" section, with why and whether the shared contract still holds. If the design is wrong in a way you can't absorb, stop and report.
5. **Spec gaps.** Anything the decisions don't settle that you had to choose goes in your report and in RATIONALE.md, one line each, citing the decision.
6. Anything touching records, the audit trail, signatures, login, roles, the sample chain, results, reports or hosting needs the `part11-expert`, `iso17025-expert` and `usp-expert` reviews before merge (`CLAUDE.md`). Say in your report that they haven't run, so the coordinator dispatches them.
