# Multi-lab tenancy: what it would take, and what to decide now

Research for [#9](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/9), part of the map [#1](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/1). Sources were fetched on 2026-09-29. Implementation of multi-lab tenancy is out of scope. This note shapes the single-lab design so that multi-lab stays cheap to add later.

## Short answer

- **Build one lab now, but make "lab" an explicit owner of data from day one.** Every lab-owned row carries a non-null `lab_id`. Business keys are unique per lab. Every audit entry names its lab, and each lab has its own hash chain. Vault object keys start with the lab. Users are global people who hold per-lab memberships, and roles attach to the membership, not to the person. All data access goes through one seam that requires a lab context. Each of these costs a few columns now. Adding any of them later means migrating Part 11 records, including the audit trail, which is costly.
- **If the owner commercializes, the likely model is a "bridge" (AWS) or "vertically partitioned" (Azure) deployment.** One codebase runs two ways. Small or trial labs share a pooled PostgreSQL database isolated by row-level security (RLS). Labs that demand isolation get their own dedicated deployment. The pharma QC customers decide which one they accept, so this choice waits until then (see Open questions).
- **No fetched regulation forbids shared or cloud infrastructure.** Each lab (the regulated user) stays fully responsible. It needs a formal agreement with the provider that covers audits, inspection support and an **exit strategy for its data**. Its records, audit trail and backups must be retrievable for that lab alone. That last point is the one that shapes the design: a pooled database can never be restored wholesale to fix one lab, so per-lab export and restore has to be a real operation.

## Tenancy models compared

Both clouds' guidance treats isolation as a spectrum, not a binary. Azure: "Instead of viewing isolation as a discrete property, consider it a spectrum." [[Azure tenancy models]](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models). AWS names three points on that spectrum. **Silo** gives each tenant a fully separate stack, and AWS lists "supporting challenging compliance models" as its first advantage [[AWS silo]](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/silo-isolation.html). **Pool** shares the infrastructure, and AWS names "compliance pushback" among its drawbacks, noting it is "especially true in environments where the compliance or regulatory rules for a domain impose strict constraints" [[AWS pool]](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/pool-isolation.html). **Bridge** mixes the two [[AWS core concepts]](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/core-isolation-concepts.html). Azure's "vertically partitioned" model is the same idea: "most of your customers' data and application tiers on multitenant infrastructures, but you deploy single-tenant infrastructures for customers who require higher performance or data isolation" [[Azure tenancy models]](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models).

| Model | Isolation | Cost on a ≤ $10/month box, few labs | Per-lab backup / restore / export | Schema migrations | Main pitfalls |
|---|---|---|---|---|---|
| **Dedicated deployment per lab** (silo / "automated single-tenant") | Strongest; a separate stack is the boundary | One small VM per lab; fine for a handful, grows linearly ("100 tenants probably require 100 times that cost") | Trivial: the lab's whole instance | Rolled out per lab; can be staggered | Needs deployment automation; fleet-wide reporting is harder [[Azure tenancy models]](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models) |
| **Database per lab, shared app** (horizontally partitioned) | Strong: "A client connection to the server can only access data in a single database" [[PG schemas]](https://www.postgresql.org/docs/current/ddl-schemas.html) | One Postgres server, N databases; cheap at small N | Easy: `pg_dump` one database | Must run on every database; track the schema version for each tenant [[Azure storage/data]](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data) | App must route each request to the right database; one connection pool per database |
| **Schema per lab, one database** | Medium: "a user can access objects in any of the schemas in the database they are connected to, if they have privileges" [[PG schemas]](https://www.postgresql.org/docs/current/ddl-schemas.html) | Cheapest after pooled | Per-schema dump works | Per schema, like the per-database model | `search_path` trust issues: adding a schema to it "effectively trusts all users having CREATE privilege on that schema" [[PG schemas]](https://www.postgresql.org/docs/current/ddl-schemas.html) |
| **Shared tables + `lab_id` + RLS** (pool) | Enforced by policy; only as good as the policies and the roles | Cheapest; one of everything | **Hard**: "restoring a single tenant might require you to restore the database to a separate resource and selectively recover that tenant's data" [[Azure storage/data]](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data) | Once | Bypass rules, covert channels and view semantics (below); "can be complex to design, implement, test, and maintain" [[Azure storage/data]](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data) |

Azure also lists **table-per-tenant** inside one database as an antipattern [[Azure storage/data]](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data). It recommends modeling the solution as a redeployable "stamp" even when the database inside is multitenant: "By modeling your solution as a stamp, you can easily redeploy it as new business opportunities arise" (same source). For this project, that means keeping the single-lab build reproducible from scripts so that a second, dedicated lab instance is a redeploy, not a fork.

### PostgreSQL RLS facts that matter if the pooled option is ever used

All quotes are from the PostgreSQL 18 docs.

- **Default deny.** "If no policy exists for the table, a default-deny policy is used." [[PG RLS]](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). Policies only apply once `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` has run [[CREATE POLICY]](https://www.postgresql.org/docs/current/sql-createpolicy.html).
- **Who bypasses RLS.** "Superusers and roles with the `BYPASSRLS` attribute always bypass the row security system … Table owners normally bypass row security as well", unless `FORCE ROW LEVEL SECURITY` is set [[PG RLS]](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). So the app must connect as a role that does not own the tables. Migrations run as the owner.
- **Covert channels.** "Referential integrity checks, such as unique or primary key constraints and foreign key references, always bypass row security" [[PG RLS]](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). A globally unique sample number would let lab A detect lab B's numbers. Business keys should be unique per `(lab_id, …)`.
- **Views run as their owner by default.** "Permission checks and policies for the tables which are referenced by a view will use the view owner's rights … except if the view is defined using the `security_invoker` option" [[CREATE POLICY]](https://www.postgresql.org/docs/current/sql-createpolicy.html); see also [[CREATE VIEW]](https://www.postgresql.org/docs/current/sql-createview.html). Reporting views would need `security_invoker = true`.
- **Permissive policies are OR-ed, restrictive ones AND-ed** [[CREATE POLICY]](https://www.postgresql.org/docs/current/sql-createpolicy.html). A tenant boundary belongs in a `RESTRICTIVE` policy, so a later permissive policy (for example, one letting a Customer see its own samples) cannot widen it across labs.
- **Tenant context.** The docs' examples key policies on `current_user`. With a shared app role, the usual approach is a custom setting read by `current_setting(...)` and set with `set_config(name, value, is_local)`. When `is_local` is true, "the new value will only apply during the current transaction" [[PG admin functions]](https://www.postgresql.org/docs/current/functions-admin.html). The transaction-local form is the one that is safe with a connection pooler. Azure notes the context has to reach the database on every query: "you need to ensure that the user's identity and tenant identity are propagated through the application and into the data store with each query" [[Azure storage/data]](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data). It also warns that RLS may need extra indexes [[Azure PostgreSQL]](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/service/postgresql).
- **Backups.** `pg_dump` sets `row_security` to `off` by default, which makes filtered queries error rather than silently return partial data. The setting "has no effect on roles which bypass every row security policy" [[PG client config]](https://www.postgresql.org/docs/current/runtime-config-client.html).
- **Isolation is not authentication.** AWS: "a user could be authenticated and authorized, and still access the resources of another tenant" [[AWS tenant isolation]](https://docs.aws.amazon.com/whitepapers/latest/saas-architecture-fundamentals/tenant-isolation.html). Both vendors say to test for cross-tenant leakage explicitly [[Azure tenancy models]](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models).

## Per-lab implications

### Audit trail

What the audit trail must contain comes from the sources below. Multi-lab changes whose trail each entry belongs to.

- Part 11 requires "secure, computer-generated, time-stamped audit trails to independently record the date and time of operator entries and actions that create, modify, or delete electronic records" (§11.10(e)) [[21 CFR 11]](https://www.ecfr.gov/current/title-21/chapter-I/subchapter-A/part-11). FDA defines an audit trail as a record "that allows for reconstruction of the course of events" (Q1c) [[FDA DI Q&A 2018]](https://www.fda.gov/media/119267/download).
- The draft revised Annex 11 (July 2025 consultation) §12.2 requires the user, "the user's role, if users may have more than one role", old and new values, the time "including the time zone if applicable", and the reason. §12.3 says audit settings may only be changed by "a system administrator not involved in any GMP activities". §12.4 says all users should be able to sort and search the trail [[Annex 11 draft 2025]](https://health.ec.europa.eu/document/download/40231f18-e564-4043-94de-c031f813d38b_en?filename=mp_vol4_chap4_annex11_consultation_guideline_en.pdf). The Commission's EudraLex Volume 4 page still listed the January 2011 Annex 11 as current when fetched [[EudraLex Vol 4]](https://health.ec.europa.eu/medicinal-products/eudralex/eudralex-volume-4_en). Treat the draft as the direction of travel, not the rule in force.

What this means for multi-lab:

1. **Each entry names its lab, and each lab has its own chain.** A lab's auditor or inspector must be able to review and verify that lab's trail without seeing another lab's entries. One global hash chain would make verifying one lab depend on every other lab's data.
2. **The acting role is resolved within the lab.** The same person may be an Analyst in one lab and a Reviewer in another, so the entry stores the role held in that lab at that moment (draft §12.2).
3. **Time zone comes from the lab.** Store UTC and record the lab's time zone. Two labs on one server may sit in different zones.
4. **Platform-operator actions go into the affected lab's trail.** When the vendor's staff migrate, repair or restore data, the entry must appear in that lab's trail, attributed to a named person. Changes that span labs (a release, a configuration change) also need a platform change log that labs can see (Annex 11 §10: "Any changes to a computerised system including system configurations should only be made in a controlled manner") [[Annex 11 (2011)]](https://health.ec.europa.eu/system/files/2016-11/annex11_01-2011_en.pdf).
5. **Access changes are audited per lab.** Annex 11 §12.3: "Creation, change, and cancellation of access authorisations should be recorded" [[Annex 11 (2011)]](https://health.ec.europa.eu/system/files/2016-11/annex11_01-2011_en.pdf). Granting or revoking a membership is an event in that lab's trail.

### Document vault

- Each lab runs its own quality system, and its QA authorizes its own SOPs. Vault documents are therefore lab-owned. Nothing is shared and editable across labs. If the platform ever ships templates, they should be read-only and copied into a lab when adopted, after which the lab owns its copy and its lifecycle.
- Records must stay accessible "throughout the retention period" (Annex 11 §7.1), and archives must stay retrievable across system changes (§17) [[Annex 11 (2011)]](https://health.ec.europa.eu/system/files/2016-11/annex11_01-2011_en.pdf). Part 11 §11.10(c) says the same [[21 CFR 11]](https://www.ecfr.gov/current/title-21/chapter-I/subchapter-A/part-11). Retention periods can differ by lab, so retention belongs in lab settings, not constants.
- Storage keys prefixed per lab (`labs/{lab_id}/…`) cover everything from a shared bucket to a separate bucket per lab. Azure treats per-tenant containers or accounts as the standard options, and advises careful authorization if containers are shared [[Azure storage/data]](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data).

### Identity and access

- **Unique people, never shared accounts.** Part 11 §11.100(a): "Each electronic signature shall be unique to one individual and shall not be reused by, or reassigned to, anyone else". §11.300(a) requires unique ID and password combinations [[21 CFR 11]](https://www.ecfr.gov/current/title-21/chapter-I/subchapter-A/part-11). FDA Q5: with shared logins "a unique individual cannot be identified" [[FDA DI Q&A 2018]](https://www.fda.gov/media/119267/download). Draft Annex 11 §11.1: "All users should have unique and personal accounts" [[Annex 11 draft 2025]](https://health.ec.europa.eu/document/download/40231f18-e564-4043-94de-c031f813d38b_en?filename=mp_vol4_chap4_annex11_consultation_guideline_en.pdf).
- **One identity per person, many memberships.** Azure: "Use a single identity for each person when possible", and key authorization and auditing on an immutable ID rather than the email or login name, "because UPNs can change" [[Azure identity]](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/identity). The model is `person` → `membership(person, lab, role…)`. The TOTP second factor belongs to the person. Roles and training records belong to the membership, because training gates assignment per lab.
- **Explicit lab context.** When one person can reach several tenants, Azure asks for "a clear mechanism … to switch between tenants" that "prevents accidental cross-tenant access" [[Azure identity]](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/identity). AWS describes authentication returning "the user's binding to a tenant" as context that "flows through all of our interactions" [[AWS identity and isolation]](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/identity-and-isolation.html). The session should hold the current lab, and every signature is recorded against it.
- **Administrator independence gains a layer.** FDA Q4: "The system administrator role … should be assigned to personnel independent from those responsible for the record content" [[FDA DI Q&A 2018]](https://www.fda.gov/media/119267/download). PIC/S adds that "QC supervisors and managers should not be assigned as the system administrators" for their own lab's systems [[PIC/S PI 041-1]](https://picscheme.org/docview/4234). Multi-lab ends up with two admin tiers: the **platform operator** (vendor staff, independent of every lab, not a lab user) and the **lab Admin** (manages memberships in one lab). The map's existing Admin role becomes the lab Admin. Platform operators need their own audited path, not a hidden superuser login in the app.
- **Later, not now:** federation with a lab's own identity provider and SCIM provisioning, which enterprise pharma customers commonly ask for [[Azure identity]](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/identity). Azure also advises against building your own identity provider (same source). That bears on [#7](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/7) if the product is ever sold.

## Regulatory considerations for shared or cloud hosting

- **Responsibility stays with the lab.** Draft Annex 11 §7.1: relying on a service provider "does not change the requirements … The regulated user remains fully responsible" [[Annex 11 draft 2025]](https://health.ec.europa.eu/document/download/40231f18-e564-4043-94de-c031f813d38b_en?filename=mp_vol4_chap4_annex11_consultation_guideline_en.pdf). PIC/S 9.1.10: "the regulated entity retains the responsibility to ensure that outsourced services are managed and assessed in accordance with GMP/GDP requirements" [[PIC/S PI 041-1]](https://picscheme.org/docview/4234). FDA counts "cloud infrastructure" among the "computer or related systems" of §211.68 (Q1f) [[FDA DI Q&A 2018]](https://www.fda.gov/media/119267/download).
- **A formal agreement is required.** Annex 11 (2011) §3.1 requires "formal agreements" with "clear statements of the responsibilities of the third party" whenever a third party is used to host, maintain or retain a system [[Annex 11 (2011)]](https://health.ec.europa.eu/system/files/2016-11/annex11_01-2011_en.pdf). Draft §7.5 lists what the contract must cover: activities and documentation, SLAs and KPIs, supplier audits, "support during regulatory inspections", communication of quality and security issues, and "an exit strategy by which the regulated user may retain control of system data" [[Annex 11 draft 2025]](https://health.ec.europa.eu/document/download/40231f18-e564-4043-94de-c031f813d38b_en?filename=mp_vol4_chap4_annex11_consultation_guideline_en.pdf). The exit strategy only works if a **complete per-lab export** (records, audit trail, signatures, vault files) exists.
- **Inspection.** "All records required under CGMP are subject to FDA inspection", including copying of electronic data (Q17) [[FDA DI Q&A 2018]](https://www.fda.gov/media/119267/download). On shared infrastructure, an inspector at lab A must be able to see everything of A's and nothing of B's, so read-only inspection views need to be scoped to one lab.
- **Backups.** Draft Annex 11 §16 requires regular backups that are physically and logically separated from the original, plus documented restore tests [[Annex 11 draft 2025]](https://health.ec.europa.eu/document/download/40231f18-e564-4043-94de-c031f813d38b_en?filename=mp_vol4_chap4_annex11_consultation_guideline_en.pdf). In a pooled database, restoring the whole database for one lab would roll back other labs' GxP records. Per-lab restore therefore has to be selective, and should be designed and tested before a second lab exists (see the Azure restore quote above).
- **One release changes every lab at once.** Each lab validates its own intended use, and Annex 11 §10 requires controlled change. Azure warns that with shared infrastructure "changes might affect your entire customer base", and that you must "know which of your tenants are on each deployment so that you can communicate information about system problems or upgrades" [[Azure tenancy models]](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models). Commercially, this is the strongest argument for dedicated deployments for labs with strict change control. Pooled labs would need notice before releases and versioned release notes.
- **Part 11 "closed" vs "open" system.** Part 11 defines a closed system as one where "system access is controlled by persons who are responsible for the content of electronic records". Open systems carry the extra controls of §11.30 [[21 CFR 11]](https://www.ecfr.gov/current/title-21/chapter-I/subchapter-A/part-11). In a vendor-hosted multi-lab setup, the lab controls who gets accounts, but the vendor controls the infrastructure. None of the fetched sources settles how that should be classified. It is an open question for the Part 11 expert ([#10](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/10)) and does not change the data model.
- **ISO/IEC 17025.** The standard's confidentiality clause bears on keeping labs' customer data apart. The ISO text is paywalled and was not fetched here; cross-check with [#3](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/3).

## Cheap early design choices that keep the door open

Each item costs little in the single-lab build and is expensive to add once Part 11 records exist.

1. **A `lab` table with one row, and a non-null `lab_id` foreign key on every lab-owned table.** Classify each table now as *lab-owned* (samples, results, equipment, inventory, vault, ELN, deviations, training records, customers, audit entries) or *platform* (units of measure, a global reference catalog, if any). Write the classification down in the schema docs.
2. **Business keys and foreign keys scoped by lab.** Use `UNIQUE (lab_id, sample_no)` rather than a global `UNIQUE (sample_no)`. Where practical, use composite foreign keys `(lab_id, id)`, so a row in one lab structurally cannot reference a row in another. This also removes the RLS covert channel.
3. **One data-access seam that requires a `LabContext`.** No query runs without it. Set the context transaction-locally (`set_config(..., true)`) even with one lab. The app connects as a non-owner role, and migrations run as the owner. Turning on RLS later then means adding policies, not auditing every query. Enabling a `RESTRICTIVE` lab policy in the walking skeleton is optional and cheap (see Open questions).
4. **Audit entries carry `lab_id`, the actor's person ID, and the role held in that lab. Each lab has its own hash chain. Timestamps are UTC with the lab's time zone recorded.** Feed this into [#13](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/13).
5. **Identity is split from the start: `person` (credentials, TOTP) and `membership` (lab, roles, training).** Key everything on immutable IDs, never on email. E-signatures record person, lab and meaning.
6. **Two admin tiers in the role model.** Lab Admin is a lab-scoped role. Platform Operator stays outside every lab, is never a lab user, and has its own audited actions. Even single-lab needs this for FDA Q4 independence.
7. **Vault object keys prefixed `labs/{lab_id}/`.** No cross-lab document references.
8. **Per-lab settings instead of constants:** time zone, retention periods, report and CoA header, numbering formats.
9. **"Export one lab" as a first-class, tested operation.** Today it equals a full export. It also serves Part 11 §11.10(b) copies, archiving (Annex 11 §17), selective restore, and the contractual exit strategy.
10. **Reproducible deployment from scripts.** That makes a dedicated second-lab instance (silo) a redeploy. It overlaps with [#6](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/6) and [#14](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/14).

**Not worth doing now:** tenant routing, lab slugs in URLs, schema-per-lab or database-per-lab scaffolding, per-lab encryption keys, federation or SCIM, a tenant-switcher UI. The choices above keep all of these options open without building any of them.

## Open questions for the owner

1. **Would target pharma QC customers accept a pooled (shared-database) deployment, or insist on dedicated instances?** This decides whether RLS pooling is ever built, or whether multi-lab means automated dedicated deployments only. The data model above supports both, so nothing blocks the single-lab build.
2. **Can a Customer organization be shared across labs?** For example, one sponsor sending samples to two labs on the platform through one portal login. The recommendation is to keep the Customer lab-owned for now, which means per-lab portal memberships.
3. **Enable a restrictive RLS lab policy in the walking skeleton now?** It is cheap, proves the seam works, and costs some complexity in tests. This belongs in [#5](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/5) or [#14](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/14), and assumes PostgreSQL is chosen.
4. **Part 11 closed vs open classification for a vendor-hosted instance.** Refer to the Part 11 expert ([#10](https://github.com/zhipengzhu1-dotcom/09-28-2026-LIMS/issues/10)).
